5: ## Project Overview
6: 
7: `mlt` (pronounced "melt") is an ultra-fast, extensible linter for MATLAB written in Rust. It uses `tree-sitter-matlab` for parsing and is architecturally inspired by [ruff](https://github.com/astral-sh/ruff) and [rumdl](https://github.com/rvben/rumdl).

40: ## Architecture
41: 
42: ### Lint Engine Flow
43: 
44: 1. CLI loads `.mlt.toml` → parses into `Config`
45: 2. `mlt_rules::active_rules(&config)` → constructs only enabled rules (filtered by per-rule and per-category config)
46: 3. `RuleRegistry::new(rules, &config)` → indexes rules by `target_node_types()`, resolves effective severity per rule (per-rule > per-category > rule default)
47: 4. `Linter::new(registry)` → initializes tree-sitter parser with MATLAB grammar
48: 5. `linter.lint(source, file_path)` → single-pass DFS traversal:
49:    - For each node: O(1) lookup of subscribed rules, dispatch `rule.check(&NodeContext)`
50:    - After traversal: call `rule.check_file(&FileContext)` only on rules where `has_file_check() == true`
51:    - Stamp effective severity (config override) onto all diagnostics
52:    - Return sorted diagnostics
53: 
54: ### Rule Trait
55: 
56: ```rust
57: pub trait Rule: Send + Sync {
58:     fn id(&self) -> &'static str;                          // e.g., "NOSEMI"
59:     fn description(&self) -> &'static str;                 // One-line summary
60:     fn severity(&self) -> Severity;                        // Default severity
61:     fn category(&self) -> Category;                        // Rule category for bulk config
62:     fn target_node_types(&self) -> &'static [&'static str]; // Node types to subscribe to
63: 
64:     fn can_be_disabled(&self) -> bool { true }             // false for critical checks
65:     fn has_file_check(&self) -> bool { false }             // true if check_file is implemented
66: 
67:     fn check(&self, ctx: &NodeContext) -> Vec<Diagnostic> { vec![] }      // Per-node
68:     fn check_file(&self, ctx: &FileContext) -> Vec<Diagnostic> { vec![] } // Per-file
69: }
70: ```
71: 
72: - **Node-level rules**: Implement `check()`, return non-empty `target_node_types()`.
73: - **File-level rules**: Implement `check_file()`, set `has_file_check() → true`, return empty `target_node_types()`.
74: - **Hybrid**: Implement both (rare).

231: ## Key Patterns and Conventions
232: 
233: ### Rule ID Convention
234: 
235: Rule IDs match MATLAB Code Analyzer check IDs exactly (e.g., `NOSEMI`, `AGROW`, `PFBNS`, `naming.class.casing`). This gives users familiar IDs and enables feature parity tracking.
236: 
237: ### Data-Driven Rules
238: 
239: For large groups of similar checks (Compatibility: ~1800, Suggested Improvements: ~243), use data-driven lookup tables:
240: 
241: ```rust
242: // Load from embedded TOML data file
243: const DATA: &str = include_str!("data/compatibility.toml");
244: ```
245: 
246: A single rule module handles many check IDs by matching function names against a lookup table.
247: 
248: ### Generic Rule Engines
249: 
250: For systematic patterns (Naming: 81 checks = 9 entities x 9 check types), implement a single generic engine parameterized by configuration.
251: 
252: ### Tree-sitter Node Types
253: 
254: The MATLAB grammar (tree-sitter-matlab 1.3) defines these important node types:
255: 
256: - **Statements**: `assignment`, `function_call`, `command`, `for_statement`, `if_statement`, `while_statement`, `switch_statement`, `try_statement`, `return_statement`, `break_statement`, `continue_statement`
257: - **Expressions**: `binary_operator`, `boolean_operator`, `comparison_operator`, `unary_operator`, `postfix_operator`, `number`, `string`, `identifier`, `function_call`, `field_expression`, `cell`, `matrix`, `range`, `lambda`
258: - **Structural**: `source_file`, `block`, `function_definition`, `class_definition`, `properties`, `methods`, `arguments_statement`
259: - **OOP**: `attributes`, `attribute`, `enumeration`, `enum`, `events`, `property`, `superclasses`
260: - **Statement parents**: `source_file`, `block` (use these to determine if a node is at statement level)
261: 
262: **Important limitation**: `function_call` is used for both actual function calls AND array/cell indexing. The grammar cannot distinguish them.
263: 
264: ### Checking Statement-Level Context
265: 
266: Many rules need to know if a node is a statement (top-level in a block) vs. a sub-expression. Pattern:
267: 
268: ```rust
269: let is_statement_level = node
270:     .parent()
271:     .map(|p| ["source_file", "block"].contains(&p.kind()))
272:     .unwrap_or(false);
273: ```
274: 
275: ### Fix Construction
276: 
277: ```rust
278: // Simple insertion
279: Fix::insert(byte_offset, ";")
280: 
281: // Replacement
282: Fix::new(start..end, "replacement_text")
283: 
284: // Multi-edit (atomic)
285: Fix::with_additional(primary_range, primary_replacement, vec![
286:     Fix::new(other_range, other_replacement),
287: ])
288: ```
289: 
290: ### Rule Config Pattern
291: 
292: Every rule should define a `#[derive(Deserialize, Default)]` config struct, even if currently empty. This makes adding parameters non-breaking:
293: 
294: ```rust
295: #[derive(Debug, Clone, Deserialize, Default)]
296: pub struct RuleIdConfig {
297:     #[serde(default)]
298:     pub some_param: Vec<String>,
299: }
300: ```

# Rule Implementation Pipeline (Planner → Reviewer → Implementer)

Every new MATLAB Code Analyzer rule in `mlt` is implemented via an independent,
three-stage flow. Flows for different rules are fully independent and run in
**parallel**.

## The three agents

| Step | Subagent (`subagent_type`) | Model | Output |
|------|---------------------------|-------|--------|
| 1. Planner | `planner` | `opencode/deepseek-v4-flash-free` | Implementation plan |
| 2. Reviewer | `reviewer` | `opencode/laguna-s-2.1-free` | Verdict + corrected plan |
| 3. Implementer | `implementer` | `opencode/deepseek-v4-flash-free` | Code, tests, docs + verification |

Agents are defined in `.opencode/agent/{planner,reviewer,implementer}.md`.

## Rule context lookup

Before planning, the rule's official context (description, severity, examples) MUST be
looked up at:
`https://www.mathworks.com/help/matlab/matlab_env/index-of-code-analyzer-checks.html`
using Playwright (`playwright_browser_navigate` → `playwright_browser_find` →
`playwright_browser_snapshot`). MathWorks returns HTTP 403 to plain `webfetch`, so
Playwright is required. Fallback archive:
`~/.local/share/opencode/tool-output/REDACTED`.

## Orchestration

Given a list of rule IDs (e.g. the remaining readability checks COMNL, STLOW, FLUDLR,
MFAMB, FVINR), run one full flow per rule:

1. **Launch ALL Planners in parallel** — one `task` call per rule, all in a single
   message, `subagent_type: "planner"`, prompt includes the rule ID and its category.
   Do not wait between them.
2. **Collect the plans**, then **launch ALL Reviewers in parallel** — one per plan,
   `subagent_type: "reviewer"`, prompt includes the rule ID, the category, and the
   plan text.
3. **Collect the verdicts**, then **launch ALL Implementers in parallel** — one per
   approved/corrected plan, `subagent_type: "implementer"`, prompt includes the rule
   ID, the category, and the plan text. Skip a rule only if the Reviewer rejects it
   outright with no usable plan; otherwise pass the corrected plan through.

Do not serialize these flows. Each of the three stages is a batch of parallel tasks.

## Completion criteria per rule

- `cargo build` succeeds
- `cargo clippy --all-targets` passes with zero warnings
- `cargo test` passes (fires, not-fires, and config tests from the plan)
- Docs updated: `docs/<rule_id>.md`, `docs/rules.md`, `zensical.toml`
- `crates/mlt_rules/src/lib.rs` has the `pub mod` line for any new module

## Notes

- Do not commit changes unless the user explicitly asks.
- If the tree-sitter grammar cannot represent the pattern (e.g. `function_call` also
  covers indexing), the plan/review must address the ambiguity explicitly.
