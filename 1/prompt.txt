All three are **Severity::Warning**, gated on the engine's check-enabling. The `CompatibilityEngine` is a zero-sized struct; check how `check_forward_gates.rs` gates individual checks (it doesn't gate via config since COMPAT engine has no disabled list — verify; if there's no per-check gate, that's fine and matches the other generic checks).

1. **IDISVARLOW** "To avoid a potential conflict with functions on the path, explicitly define the variable before indexing into it." — file-level. Walk the tree for `function_call`/indexing patterns where a variable is indexed (`x(i)`, `x{i}`, `x.field`) BEFORE it is assigned anywhere in the enclosing scope. Use `SymbolTable`: if a name has a `use` at an offset earlier than any `def` of that name in the same scope, and the use is an indexing context (the identifier is followed by `(`/`{`), fire IDISVARLOW on the use. Conservative: skip if the name is a builtin (`true,false,pi,inf,nan,eps,i,j,end,ans,varargin,varargout`) or a known function call (the identifier is the callee name of a `function_call`). 
2. **IDISVARHIGH** "Variable must be explicitly defined before first use. In some cases, the definition was not required in previous releases, but it is now required." — file-level. Like IDISVARLOW but fires for ANY first use (read) of a name that has no prior definition in scope, where the name is NOT a callee (so plain reads like `x + 1` or passing `x` to a function). Conservative: only fire when the symbol table shows a use with zero prior defs in the same scope and the identifier is not a function-call callee and not a builtin. Distinguish from existing `NODEF` (in `unset_variables/`) — the plan: IDISVARHIGH is the strict behavior-change variant; keep your detection narrow (only clear first-use-before-def, not branch-partial cases).
3. **SHVAI** "Explicitly define shared variables in the parent function before calling the nested function. MATLAB does not share uninitialized variables between a nested function and the parent function." — file-level. Detect: a nested function scope reads/writes a variable `x` that is ALSO used in the parent function, but `x` has no definition in the parent BEFORE the nested function's definition. Use `SymbolTable`: find `ScopeKind::NestedFunction` scopes; for each name used inside the nested function, check the parent scope — if the parent has defs of that name but all occur at offsets AFTER the nested function's start offset (so the shared var is not initialized before the nested function), fire SHVAI on the nested function node or the first parent def. Conservative: only fire when the parent has NO def before the nested function start.
